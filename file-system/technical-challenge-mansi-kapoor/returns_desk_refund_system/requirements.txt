RETURNS DESK REFUND SYSTEM — REQUIREMENTS
==========================================
(Design-planning notes distilled from readme.md. Update this file as new
stages/requirements are introduced.)

1. PURPOSE
----------
- Build an extensible library that processes return requests and decides:
  (a) the refund amount to issue right now (may be 0.00)
  (b) the decision: AUTO_REFUND or MANUAL_REVIEW
- Must be designed to evolve — expect new rules, fields, and cross-request
  logic to be layered on in later stages.

2. INPUT CONTRACT
------------------
Each return request is a tuple with these fields (order matters):
  1. request_id           - unique identifier
  2. order_id             - unique for this exercise
  3. buyer_email          - string; may vary by casing/whitespace -> needs normalization
  4. shipping_address_id  - string; already normalized
  5. payment_fingerprint  - tokenized string; already normalized
  6. order_total          - decimal number
  7. reason               - enum: DAMAGED | NOT_RECEIVED | CHANGED_MIND

Program receives a LIST of these tuples (batch processing, not single-item).

3. OUTPUT CONTRACT
-------------------
For each input request, output a tuple:
  (request_id, refund_amount, decision)

- refund_amount: decimal, 0.00 when not auto-refunding
- decision: "AUTO_REFUND" or "MANUAL_REVIEW"
- Output order/count should correspond 1:1 with input requests.

4. STAGE 1 — BASIC REFUND RULE (functional requirements)
----------------------------------------------------------
- Each request evaluated independently (no cross-request state yet).
- Policy:
    IF reason == "DAMAGED": refund_amount = order_total, decision = AUTO_REFUND
    ELSE:                   refund_amount = 0.00,        decision = MANUAL_REVIEW
- Must match sample input/output exactly (see readme.md Stage 1).

5. NON-FUNCTIONAL / DESIGN REQUIREMENTS
------------------------------------------
- Extensibility: new reasons, new policies, thresholds, or multi-request
  (stateful) rules should be addable without rewriting core logic.
  -> Consider a strategy/rule-based design (e.g. pluggable rule chain,
     policy objects) rather than a single if/else block.
- Separation of concerns:
    - normalization/parsing of raw tuples into a typed model
    - decision/policy logic
    - output formatting back into tuples
- Data handling:
    - buyer_email should be normalized (trim + lowercase) before any
      comparison/grouping logic is applied later.
    - order_total should be treated as a precise decimal (avoid float
      rounding issues) — likely use Decimal.
    - reason should be validated against the known enum values.
- Testability: core decision logic should be unit-testable without I/O.
- Language: implementer's choice (per parent README); confirm which
  language/runtime will be used before finalizing structure.

6. OPEN QUESTIONS / UNKNOWNS (to clarify or assume before coding) followed by answers
---------------------------------------------------------------------
- What later stages will introduce (readme says "gradually add
  requirements" — only Stage 1 is currently defined). Anticipate:
    - Per-buyer / per-payment-fingerprint / per-shipping-address
      fraud or abuse thresholds (why these fields exist beyond DAMAGED
      logic is still unclear at Stage 1 — likely used in later stages
      for cross-request signals, e.g. repeat returns detection).
    - Reason-specific rules for NOT_RECEIVED and CHANGED_MIND. There can be additional reasons as well. 
    - Partial refunds (currently only full or 0.00)- yes
    - Configurable policy thresholds (e.g. dollar limits).
- Whether MANUAL_REVIEW cases need additional metadata/reasoning attached
  in later stages.

7. Edge cases

 - if there's no reason indicated for return then it should go for manual MANUAL_REVIEW
 - if request_id is missing then return "ERROR". 
 - if buyer_email is missing then return "ERROR". 
 - if shipping_address_id is missing then return "ERROR". 
 - if payment_fingerprint is missing then return "ERROR". 
 - if order_total is missing then return "ERROR". 



8. SUGGESTED DESIGN SKETCH (for planning)
---------------------------------------------
- ReturnRequest (typed model) <- parsed/normalized from raw tuple
- RefundDecision (typed result) -> serialized to output tuple
- Rule / Policy interface: evaluate(request, context) -> RefundDecision
- RuleEngine / DecisionPipeline: runs one or more rules per request,
  first-match-or-composite depending on how requirements evolve
- process_return_requests(requests: list[tuple]) -> list[tuple]:
    entry point that ties parsing -> engine -> formatting together

9. IMPLEMENTATION (what has actually been built, and where)
-----------------------------------------------------------
Package: returns_desk_refund_system/ (import as `returns_desk_refund_system`)

There are two parallel surfaces on top of the same shared building blocks:

  A) process_return_requests(requests, daily_auto_refund_cap=200.00)
     - request_processor.py
     - Stateless, tuple-in/tuple-out entry point matching readme.md's
       Stage 1 + Stage 2 contract exactly. No pre-registered Order data
       needed — order_total is taken directly from each input tuple.
     - Implements:
         * Stage 1 policy (DAMAGED -> AUTO_REFUND full order_total; else
           -> MANUAL_REVIEW, 0.00)
         * Stage 2 per-buyer daily auto-refund cap (default $200), tracked
           via a running total across one call ("one call = one day")
         * Section 7 edge cases: missing reason -> MANUAL_REVIEW; missing
           request_id / buyer_email / shipping_address_id /
           payment_fingerprint / order_total -> "ERROR" (literal string,
           replacing the whole result-list entry) instead of a raising
     - normalize_email(raw_email): trims + lowercases + strips dots from
       the local part only (domain untouched), used to group buyers for
       the daily cap so casing/whitespace/dot variants count as one buyer.
     - Decision is split into two composable steps so future stages can
       extend either independently:
         _base_decision()   -> Stage 1 policy
         _apply_daily_cap() -> Stage 2 adjustment (only when Stage 1
                                would auto-refund)

  B) ReturnDeskService (stateful, order-aware workflow)
     - service.py
     - Models a Returns Desk that already knows about orders (with
       line-item detail), and a return moving through a status lifecycle,
       rather than a single-shot batch of flat tuples.
     - __init__(self, orders: dict[str, Order], decision_engine=None)
     - submit_return(order_id, items, reason, actor="customer")
         -> validates order exists, reason is a known enum value, and
            requested items/quantities are part of the order and not
            already claimed by another non-rejected return; creates a
            ReturnRequest in REQUESTED status.
     - evaluate_return(return_id) -> RefundDecision
         -> runs the request through RefundDecisionEngine (refund_policy.py)
            and caches the result on the ReturnRequest.
     - Only submit_return + evaluate_return exist today; approve/receive/
       refund/reject/close transitions are not yet implemented (see
       status.VALID_TRANSITIONS, already defined for when they are).

Shared building blocks (used by both A and B where applicable):
  - reasons.py      RETURN_REASONS = {DAMAGED, NOT_RECEIVED, CHANGED_MIND}
  - decisions.py    REFUND_DECISIONS = {AUTO_REFUND, MANUAL_REVIEW}
  - status.py        RETURN_STATUSES + VALID_TRANSITIONS (B only, for now)
  - models.py        Order, OrderItem, ReturnRequest, ReturnLineItem,
                      RefundDecision
  - exceptions.py    ReturnDeskError and subclasses (OrderNotFoundError,
                      InvalidReturnItemsError, InvalidReturnReasonError,
                      ReturnNotFoundError, InvalidStatusTransitionError,
                      MissingRequiredFieldError)
  - refund_policy.py RefundRule (ABC) / DamagedItemsAutoRefundRule /
                      DefaultManualReviewRule / RefundDecisionEngine
                      (used by ReturnDeskService.evaluate_return; the raw
                      tuple flow in request_processor.py currently
                      re-implements the equivalent Stage 1 check inline
                      since it works off order_total rather than
                      line-item unit prices — worth revisiting if the two
                      surfaces need to share one policy implementation)

Known gap: request_processor.py's per-request policy and
refund_policy.py's RefundDecisionEngine are two separate implementations
of "the same" Stage 1 rule (one keyed on order_total, one on order line
items). If a future stage needs identical policy behavior in both
surfaces, consider unifying them behind one shared rule interface.

10. TESTS
---------
Location: returns_desk_refund_system/tests/ (pytest, uses fixtures +
@pytest.mark.parametrize)

  - test_request_processor.py  process_return_requests + normalize_email
      * Stage 1 sample from readme.md (exact input/output)
      * Stage 2 sample from readme.md (exact input/output, $200 cap)
      * decision-by-reason matrix (DAMAGED/NOT_RECEIVED/CHANGED_MIND/
        missing/blank/unrecognized reason)
      * missing-required-field -> "ERROR" matrix (all 5 required fields)
      * daily cap: under cap, exact boundary, over cap (partial refund),
        cap already exhausted, cap tracked per normalized buyer (dots/
        casing/whitespace), cap independent across buyers, non-auto-
        refund requests don't consume the cap, "ERROR" requests don't
        consume the cap, custom cap value
      * data handling: email normalization, Decimal precision, empty
        batch, non-numeric order_total -> "ERROR"
  - test_service.py            ReturnDeskService.submit_return +
                                evaluate_return
      * submit success cases (dict item, bare item id, custom actor,
        ReturnLineItem instance)
      * validation error matrix (unknown order, invalid reason, item not
        in order, empty items, non-positive/over-limit quantity)
      * stateful in-flight quantity tracking + rejection freeing quantity
      * evaluate_return decision matrix by reason, unknown return_id
  - test_refund_policy.py      RefundDecisionEngine
      * defensive fallback to MANUAL_REVIEW when no rule matches
